# Phase 2: Contract Foundation - Research

**Researched:** 2026-04-05
**Domain:** Solidity ERC-20 contract (OpenZeppelin v5 ERC20Capped, Hardhat 3 TypeChain)
**Confidence:** HIGH

## Summary

Phase 2 replaces the Phase 1 Placeholder contract with a RoxasToken.sol that inherits ERC20 and ERC20Capped from OpenZeppelin v5.6.1. The contract hardcodes name ("Roxas Token"), symbol ("RXS"), and a 10M cap (with 18 decimals). No minting in constructor -- totalSupply starts at 0. After compilation, TypeChain generates typed contract interfaces in the `types/ethers-contracts/` directory.

The critical technical finding is that explicitly inheriting both `ERC20` and `ERC20Capped` (as specified in CONTEXT.md) requires a mandatory `_update()` override due to Solidity's diamond inheritance rules. This was verified by attempting compilation without the override, which produces `TypeError: Derived contract must override function "_update"`. The override is simple (`super._update(from, to, value)`) but forgetting it causes a compilation failure.

Additionally, Hardhat 3's TypeChain plugin generates types to `types/ethers-contracts/` (NOT the Hardhat 2 `typechain-types/` directory). The current `.gitignore` excludes `typechain-types/` but not `types/`, which needs correction in this phase.

**Primary recommendation:** Follow the CONTEXT.md dual-inheritance pattern (`is ERC20, ERC20Capped`) with the required `_update()` override. Update `.gitignore` to exclude `types/` instead of the stale `typechain-types/` entry.

### Pattern 1: Dual Inheritance with _update Override (REQUIRED)

**What:** When explicitly listing both `ERC20` and `ERC20Capped` in the inheritance chain, Solidity requires an explicit `_update()` override to resolve the diamond inheritance conflict. Both ERC20 and ERC20Capped define `_update()`, so the compiler needs to know which one the derived contract intends to use.

**Why required:** Verified by compilation test. Without the override, solc produces:
```
TypeError: Derived contract must override function "_update".
Two or more base classes define function with same name and parameter types.
```

**Verified pattern (compiles successfully):**
```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.28;

import {ERC20} from "@openzeppelin/contracts/token/ERC20/ERC20.sol";
import {ERC20Capped} from "@openzeppelin/contracts/token/ERC20/extensions/ERC20Capped.sol";

/// @title RoxasToken (RXS) - ERC-20 with capped supply
/// @notice ERC-20 token with a hard cap of 10,000,000 RXS
contract RoxasToken is ERC20, ERC20Capped {
    constructor()
        ERC20("Roxas Token", "RXS")
        ERC20Capped(10_000_000 * 10 ** 18)
    {}

    /// @dev Required override to resolve ERC20 vs ERC20Capped _update conflict.
    /// ERC20Capped._update() enforces totalSupply() <= cap() on every mint.
    function _update(address from, address to, uint256 value)
        internal
        override(ERC20, ERC20Capped)
    {
        super._update(from, to, value);
    }
}
```

**Confidence:** HIGH -- compiled and tested locally against installed OZ v5.6.1.

### Pattern 3: TypeChain Auto-Generation in Hardhat 3

**What:** The hardhat-typechain plugin (v3.0.5) runs automatically after every successful compilation. It generates TypeScript types to `types/ethers-contracts/` by default.

**Key differences from Hardhat 2:**
- Output directory: `types/` (NOT `typechain-types/`)
- Target: always `ethers-v6` (hardcoded in plugin)
- Module format: ESM-compatible (imports use `.js` extensions, `node16Modules: true`)
- Types include: contract interfaces, typed factories, common types, and HRE module augmentation (`hardhat.d.ts`)

**What gets generated for an ERC-20 contract:**
- `types/ethers-contracts/RoxasToken.ts` -- typed contract interface with all function signatures
- `types/ethers-contracts/factories/RoxasToken__factory.ts` -- typed factory for deployment
- `types/ethers-contracts/common.ts` -- shared types (TypedContractEvent, etc.)
- `types/ethers-contracts/index.ts` -- barrel export
- `types/ethers-contracts/hardhat.d.ts` -- HRE augmentation for `ethers.getContractFactory("RoxasToken")`

**Confidence:** HIGH -- verified by compiling a test ERC20 contract and inspecting the generated output.

### Anti-Patterns to Avoid

- **Using `is ERC20Capped` alone without `is ERC20`:** While this compiles and works (ERC20Capped inherits ERC20), the CONTEXT.md explicitly specifies dual inheritance. Follow the locked decision.
- **Adding constructor parameters:** The cap, name, and symbol are hardcoded. Do not accept them as constructor args.
- **Minting in constructor:** Explicitly deferred to Phase 4. The constructor must be empty (no `_mint` call).
- **Overriding `_beforeTokenTransfer`:** This is an OZ v4 pattern. OZ v5 uses `_update()` exclusively.
- **Using revert strings:** OZ v5 uses custom errors (`ERC20ExceededCap`, `ERC20InvalidCap`). Do not add revert string checks.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| ERC-20 standard functions | Manual balanceOf/transfer/approve | OpenZeppelin ERC20 | Audited, handles edge cases (zero address, overflow, approval race condition) |
| Supply cap enforcement | Manual totalSupply check in mint | ERC20Capped._update() | Enforces cap at the `_update` level -- catches ALL minting paths (including internal `_mint`) |
| TypeScript contract types | Manual type definitions | TypeChain auto-generation | Types derived from actual ABI -- always in sync with contract |

**Key insight:** The entire Phase 2 contract is essentially OpenZeppelin composition. The only custom code is the `_update()` override (which just calls `super._update()`). Do not add any custom logic beyond what CONTEXT.md specifies.

## Common Pitfalls

### Pitfall 1: Forgetting the _update Override
**What goes wrong:** Inheriting both ERC20 and ERC20Capped without overriding `_update()` causes a compilation error.
**Why it happens:** Developers assume ERC20Capped handles everything. It does -- but only if you inherit ONLY from ERC20Capped. Dual inheritance triggers Solidity's diamond override requirement.
**How to avoid:** Always include the `_update()` override with `override(ERC20, ERC20Capped)` and `super._update(from, to, value)`.
**Warning signs:** `TypeError: Derived contract must override function "_update"` at compile time.

### Pitfall 2: Decimals Miscalculation in Cap
**What goes wrong:** Setting cap to `10_000_000` (raw) instead of `10_000_000 * 10 ** 18`. This creates a cap of 0.00000000001 tokens.
**Why it happens:** ERC-20 values are stored in smallest units (like wei). 1 RXS = 10^18 base units.
**How to avoid:** Always use `10_000_000 * 10 ** 18` in Solidity. In tests, use `ethers.parseEther("10000000")`.
**Warning signs:** `cap()` returns a suspiciously small number in tests.

### Pitfall 3: Stale .gitignore for TypeChain Output
**What goes wrong:** The current `.gitignore` excludes `typechain-types/` (Hardhat 2 convention) but NOT `types/` (Hardhat 3 convention). TypeChain output gets committed to git.
**Why it happens:** Phase 1 used the Hardhat 2 gitignore pattern because the Placeholder contract produced no TypeChain output.
**How to avoid:** Update `.gitignore`: replace `typechain-types/` with `types/` (or add `types/` alongside it).
**Warning signs:** `git status` shows untracked files in `types/` after compilation.

### Pitfall 4: OZ v4 Patterns in v5 Code
**What goes wrong:** Using `_beforeTokenTransfer`, `SafeMath`, `Counters`, or `Ownable()` without args.
**Why it happens:** Outdated tutorials dominate search results and AI training data.
**How to avoid:** Only reference OZ v5 docs. Check that imports come from `@openzeppelin/contracts/` (v5), not v4.
**Warning signs:** Compilation errors about missing functions or wrong constructor signatures.

### Pitfall 5: Floating Pragma
**What goes wrong:** Using `pragma solidity ^0.8.28;` instead of `pragma solidity 0.8.28;` (exact pin).
**Why it happens:** Many tutorials use floating pragma.
**How to avoid:** Pin to exact version matching hardhat.config.ts. Phase 1 established `0.8.28` exact pin pattern.
**Warning signs:** Different bytecode between local and CI compilation.
